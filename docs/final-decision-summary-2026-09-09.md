## 一、一句话结论

**留在 Python。主线 = 方案 1（代码重组，20-28 人日）+ 方案 8（启动/体积优化，2-5 人日）；换栈只保留一个备选 = 方案 4（WPF + .NET 10），且只以 20 人日试点的形式启动。**

核心理由一句话：你的性能痛点（打开报表页 3.6-8.4 秒）是**调用结构问题**（24 次重复全量结算），不是语言慢 —— Python 侧 8 人日改调用结构拿到 **20-100 倍提速**（降到 0.07-0.17 秒）；任何换栈方案花 130-285 人日也**解决不了同样的三大问题**，还会作废 3,911 行现有测试。

## 二、主线：方案 1 + 方案 8

### 方案 1：六阶段重组（20-28 人日 ≈ 每周 1.5 天 × 13-19 周）

| 阶段 | 内容 | 工期 | 关键验收 |
|---|---|---:|---|
| **0 安全网** | 补 `person_settlement` / `collection` 单测 + **5 个导出器 golden-file 回归**（表头序列/首行/合计行/sheet 名逐项断言）+ 固定数据集 fixture | 3-4 人日 | ≥60 用例全绿；**故意改坏任一结算口径或导出列名，测试必须红** |
| **1 消灭 N+1** | `_compute` 内 4 个字典预加载（收款/费用/员工类型/发票日期一次拉全）+ 修 4 处 `setdefault` 急切求值 + 期间条件 WHERE 下推 | 3-4 人日 | 单次 `build_settlement` 的 SQL 次数 6,000-10,000 → **<100**；输出与优化前逐位相同 |
| **2 索引与写法** | 8 条 `CREATE INDEX`；`strftime` 索引杀手改区间写法；相关子查询改 LEFT JOIN | 1.5-2 人日 | `EXPLAIN QUERY PLAN` 无全表扫描 |
| **3 调用收敛+缓存+异步** | `build_settlement_cached` + 完整失效点清单 + `_latest_data_year` 降级 + 导出/结算包 QThread + 进度条 | 3-4 人日 | 打开报表页 24 次 → **≤3 次**；导出全部员工 1+4N → **N+1**；导出期间窗口可拖动 |
| **4 导入链路** | 销项文件只解析一次（现在是两遍）+ staff_type 预加载 + INSERT 批量化 + 显式事务 | 2-3 人日 | 重导同月数据逐行一致（CSV diff 为空）；耗时下降 50%+ |
| **5 清理+局部解耦** | 合并 170 行重复代码 + 抽 QSS/tab 模板 + `settlement_repo/service` 竖切 + 76 处宽泛 except 收口 | 5-7 人日 | 总行数下降 ≥300；全链路手工回归通过 |

通用约定：每阶段独立 commit + push，回退走 `git revert`；阶段边界必须是"完整可运行"状态。
多分支安全：阶段 0-4 只动 `db/engine/importer/exporter/tests`，与你的 4 个 wt-* UI 分支（全在 `app/ui/*`）**零文件重叠**。

### 方案 8：启动/体积（2-5 人日，可与阶段 2 并行）

PyInstaller `onedir` + 延迟导入（项目已有先例）+ 排除未用模块 → 可选 Nuitka 编译（启动快 30-50%）→ 最后手段才是 Tauri 外壳 + Python 内核。
解决的是"换栈唯一真实的日常收益"（现在 100-300 MB / 1-3 秒启动），用 1/50 的成本单独拿到。

### 你拿到什么（对照三大诉求）

| 诉求 | 结果 |
|---|---|
| **性能** | 打开报表 3.6-8.4 秒 → **0.07-0.17 秒**（20-100 倍）；导入提速 50%+ |
| **可读性** | 死代码/重复消除、常量化、异常收口，总行数 -300+ |
| **可维护性** | 结算引擎/收款/导入/5 导出器首次有单测；**导出列名（你的硬要求）有机器保护**；service/repo 切断 UI 直连 db.py |

## 三、备选：方案 4（WPF + .NET 10）—— 只在触发条件出现时启动

### 推荐组合
**WPF + .NET 10（LTS 至 2028-11）+ Dapper + Microsoft.Data.Sqlite + NPOI（Apache 2.0）**

- .NET 8/9 于 **2026-11-10 EOL**（仅剩 2 个月），必须直接上 .NET 10
- NPOI 单库覆盖 .xls/.xlsx/.xlsm + 11 类导出特性（全生态唯一全绿）
- WinUI 3 出局（无第一方 DataGrid、multi-header 仍 open、大表格 open 性能 bug #309、Win7 门焊死）
- WPF 保留 Win7 后补票（multi-targeting net48 + net10.0-windows，代价 = 持续开发税 +10-15% 摩擦）
- 最有价值发现：**共享 SQLite 双轨灰度可行**（C# 直读现有 lawfirm.db → C# 只读报表先行 → 逐页交接 → 最后切写）

### 真实成本
**130-180 人日 ≈ 单人每周 1.5 天 × 1.7-2.3 年**；业务演进（退款/分成引擎/4 个 wt-* 选型）会被冻结或长期双轨；投入 60 人日后放弃残值约 40%（golden 资产除外，那个 100% 保留）。

### 启动触发条件（至少命中一条再谈）
1. 产品化对外销售（多客户部署、安装器、授权）
2. 交接给 .NET 背景的维护者
3. 业务规模增长 ~10 倍（3 万票/年）且 Python 优化后实测仍不达标
4. 你个人长期转向 C# 职业方向

### 若启动：20 人日 go/no-go 试点（不赌全量）
golden-file 安全网（3-4，**与方案 1 阶段 0 完全共用，零浪费**）→ C# 只读直连 lawfirm.db（3）→ 移植结算引擎 + golden diff 逐位对比（8-10）→ NPOI 重写 1 个导出器（3-4）。
判据：golden 全绿 + 实测提速 + **你写 C# 的体验是否愿意再写 110-160 天**。任一不满足 → 停止，golden 资产转投方案 1。

## 四、被否决的方案（速查）

| 方案 | 一句话否决理由 |
|---|---|
| Rust 全量（186-285 人日 / 2.3-3.7 年） | GUI 无生产级 Qt 替代（ritual 停维护）；`rust_xlsxwriter` 只写不读 |
| C# + WPF **现在就做** | 成本/收益不匹配，降级为触发条件下的备选 |
| Go + Wails | `excelize` 缺 .xls（你的台账三种格式） |
| TS + Electron/Tauri | ExcelJS 缺打印设置（导出打印格式会变）+ Electron 启动 2-4 秒反而更慢 + SheetJS npm 停更（CVE 修复绕行自建 CDN）+ node_modules × Seafile 灾难 |
| Java + POI | GUI 侧全谱系最差 |
| Flutter Desktop | **生态无任何开源 .xls 读取库**（一票否决）；唯一全覆盖库 Syncfusion 触发许可证红线 |
| React Native Windows | Excel 硬伤全额继承 Electron + 桥接/工具链最重 |
| WinUI 3 | 无第一方 DataGrid；WinUI.TableView 多级表头仍 open + 大表格 open 性能 bug #309 + 单人维护；Win7 门焊死；绿色单 exe 是自解压特例 |
| Avalonia UI | 本体健康（MIT/30k stars）但官方 DataGrid 缺冻结列+多级表头（自研 10-15 人日，WPF 缺口为 0）；ReoGrid 的 Avalonia 支持只在商业版 V5（触发红线）；工期 150-210 人日。**保留触发器：未来跨 Linux/国产系统时，Avalonia 反超为唯一解** |
| Rust 热点扩展（PyO3） | Rust 侧不能碰 SQLite（WAL 锁竞争），跨语言序列化吃掉收益；且结算引擎慢的根源是调用结构 |

## 0. 必须先回答的问题：**换语言能不能解决当前的性能痛点？**

### 0.1 结论（先讲死）

> **不能。当前痛点是「调用结构与查询模式问题」，不是「Python 解释器慢」。
> 换语言（含 Rust）对三大痛点的解决能力为：①重复调用 —— **完全不解决**；②架构耦合 —— **不自动解决**；③测试缺口 —— **会显著恶化**。
> 请务必先读完第 0 章再做决策，避免花 145~285 人日换栈，最后得到一个"还是慢"的结果。**

### 0.2 证据：痛点的性质判定

审计已定位的最大痛点是 `person_settlement._compute()`（368 行 / 74 分支）被**重复调用**：

| 场景 | 调用次数 | 证据 |
|---|---:|---|
| 打开「各类报表」页一次 | **≈24 次** | `settlement_view.py:146`（`_latest_data_year` 最多 4 次）+ `:159` + `:534` + `:556` + `:680` + `:829` + `showEvent:195` → `refresh:249` → `_sync_type_options:222`（3 次）+ `:251`（1 次） |
| 导出全部员工（N 人） | **1+4N 次**（N=30 → 121 次） | `person_settlement_exporter.py:159`（1 次）→ 循环 `:164` → `export_one:141`（1 次）+ `:143-144`（3 次） |

单次 `_compute` 内部还有 7 处 N+1（`person_settlement.py:160-164 / 168-172 / 150-158 / 241-244 / 250 / 271 / 274 / 286 / 289`）与 4 处 `setdefault` 急切求值（`:199 / 217 / 256 / 297`）。

**这三项全部是"调用次数"与"查询次数"问题，与语言运行时无关：**

| 问题 | 若换成 Rust 会怎样 | 判定 |
|---|---|---|
| 24 次重复调用 | Rust 里调用 24 次，仍然是 24 次。**被调用函数快 50 倍，调用次数不变，总耗时只降为 1/50**——而**改成调用 1 次就能直接降为 1/24，且零风险、2 人日** | 换语言**不解决** |
| 7 处 N+1 查询 | 瓶颈是 **SQLite 往返次数**（20,000 次单行查询）。SQLite 本身是 **C 库**，Python 侧只是"绑定 + 装箱"开销（约 3-8 μs/次）。Rust `rusqlite` 单次约 1.5 μs，**只快 2-5 倍**；而**改成 8 条批量查询能快 1000 倍** | 换语言**几乎无效** |
| `_compute` 纯计算部分 | 约 50-150 ms（3,000 票 × 6,000 笔收款的 dict 聚合）——**这才是真正受 Python 运行时影响的部分**，Rust 可快 20-50 倍 | 换语言**有效，但绝对量级小**（见 0.3） |

### 0.3 量化算账：边际收益已经进入"感知不到"区间

> **假设来源声明**：以下为**静态推演，未实测**（环境缺 `qfluentwidgets` 无法起 GUI、无生产 `data/lawfirm.db`、shell 执行环境失效）。数据量假设：年 3,000 票、30 名经办人、6,000 笔收款、200 条费用/月（基于业务描述）。SQLite 单点查时序参考 sqlite3 C 库 + Python 绑定的常规量级（2-8 μs），`rusqlite` 参考其公开基准（1-2 μs）。**每个数值都标注了假设，用户可用审计报告第 3 节给出的验证方式自行实测校准。**

| 状态 | 单次 `_compute` | 调用次数 | **打开报表页总耗时** | 相对当前 | 累计成本 |
|---|---:|---:|---:|---:|---:|
| **当前** | 150-350 ms | 24 | **3.6 - 8.4 秒** | 1× | 0 |
| + 阶段1：N+1 消除 | 70-170 ms | 24 | 1.7 - 4.1 秒 | ~2× | **4 人日** |
| + 阶段3：调用收敛 + 缓存 | 70-170 ms | **1** | **0.07 - 0.17 秒** | **20-100×** | **8 人日** |
| 换 Rust，但**不优化**调用结构 | 15-35 ms | 24 | 0.36 - 0.84 秒 | 4-23× | **90+ 人日** |
| 换 Rust，且**也优化** | 3-8 ms | **1** | 0.003 - 0.008 秒 | ~1000× | **190+ 人日** |

**这张表是本次评估的核心结论，请重点看最后两行与第 3 行的对比：**

- 花 **8 人日**做 Python 侧优化，拿到 **20-100 倍**，耗时从"卡顿 3.6-8.4 秒"变成"瞬间 0.07-0.17 秒"
- 在此基础上再花 **180+ 人日**换 Rust，只多拿 **10-50 倍**，结果是 0.15 秒 → 0.005 秒
- **0.15 秒 与 0.005 秒，用户都感知为"点开就出来"**。这 180 人日的边际收益是零。

### 0.4 为什么"换语言"在直觉上很有吸引力，但这里是陷阱

| 直觉 | 事实 |
|---|---|
| "Rust 比 Python 快 50 倍" | 成立，但**本项目 99% 的墙钟时间不在 Python 字节码上**——在 SQLite 往返、在重复调用、在 openpyxl 构建对象、在 Qt 渲染。这些都是 **C/C++ 库**在工作，Python 只是胶水 |
| "重写后代码质量会变好" | 不成立。**质量来自设计与测试，不来自语言**。带着 74 分支的 `_compute` 直译到 Rust，你会得到一个**同样难懂、且没有测试**的 Rust 版本 |
| "Rust 类型安全能防 bug" | 成立，这是**真实收益**（见 3.2）。但它是**防新 bug**，而当前最大的风险是**改坏老口径**——那要靠 golden-file 回归（语言无关） |
| "编译成单文件 exe，启动快" | **成立，这是换栈唯一用户日常可感知的收益**（PyInstaller 包约 100-300 MB / 启动 1-3 秒 → Rust 单文件 10-30 MB / <100 ms）。但它跟"结算慢"是两件事 |

### 0.5 换语言对三大问题的逐条判定（后文每个方案都要对照这张表）

| Top-3 问题 | 换语言能否解决 | 说明 |
|---|---|---|
| ① **重复调用**（24 次 / 1+4N 次） | ❌ **完全不解决** | 这是**调用点**的问题（`settlement_view.py` / `person_settlement_exporter.py`），不是被调函数的问题。任何语言里直译都会原样带过去 |
| ② **`db.py` 入度 45 + 循环依赖 `importer`（`db.py:505-507`）+ 12 个 UI 文件直连 `get_conn()`** | ⚠️ **不自动解决，但架构能力不同** | 语言不阻止你写出入度 45 的 god module。**但**：Rust/C#/Go 的模块可见性（`pub` / `internal` / 大写导出）与编译器能在**结构上强制分层**，Python 只能靠约定与 lint。这是换栈的**真实（但是间接的）收益** |
| ③ **测试缺口**（结算引擎 / 收款聚合 / 导入器 / 5 个导出器零单测） | ❌ **显著恶化** | 现有 23 个测试文件 / 3,911 行**全部作废**，需用新语言重建。**而测试缺口恰恰是所有重构的前置条件**——换栈等于把仅有的安全网先扔掉，再在没有网的情况下走钢丝 |

### 方案 1：保持 Python + 重组路线（基准线）

| 项 | 内容 |

## 5. 明确推荐

### 5.1 推荐：**方案 1（保持 Python + 重组）+ 方案 8（顺手治启动/体积）**

**不换语言。这是本次评估的正确答案，我直说。**

五条决定性理由：

1. **换语言不解决任何一个 Top-3 问题**（第 0.5 节已逐条判定）。痛点在调用点与查询模式，不在语言。
2. **边际收益落在感知不到区间**（第 0.3 节）。8 人日拿 20-100 倍（8.4 秒 → 0.17 秒）；再花 180 人日只多拿 10-50 倍（0.17 秒 → 0.005 秒）。**后者是零收益投入**。
3. **工期与用户画像根本不匹配**。所有换栈方案 131-285 人日 → 单人非全职 **1.7-3.7 年**。而业务仍在演进（退款模块、分成引擎、4 个 wt-* 选型）。**这是最高概率的结局：项目死在半路，新旧两套都不能用。**
4. **换栈会先毁掉仅有的安全网**。3,911 行测试全部作废，而在"没有测试保护"的状态下重写 74 分支的结算口径 —— 这是把当前最大的风险（口径偏差）放大数倍。
5. **用户已拒绝过一次大重写**（Flutter/WinUI3）。本次 6 个方案工期是那次的 **1.5-3 倍**，没有理由认为结论会不同。

### 5.2 如果一定要保留"换语言"的可能性：**只推荐方案 2 的一个受限试点**

如果用户在读完本文后仍想保留 Rust 的门（例如出于学习/长期技术储备的考虑），**唯一理性路径是方案 2 的小规模试点**，且必须遵守下面的边界设计。

#### 试点模块选择：**Excel 导入解析**（不是结算引擎）

> ⚠️ **关键判断：不要选结算引擎做试点。** 直觉上它最慢，但它慢的原因是调用结构与 N+1（换语言不解决），而且它有 74 个分支的精密口径（重写风险最高）。选它做试点，**大概率既拿不到收益、又引入口径 bug**，然后得出错误结论。

**应选 `app/importer/excel_reader.py` 的底层读取 + `calamine` 替换 `xlrd`/`openpyxl` 读取侧**，理由：

| # | 理由 |
|---|---|
| 1 | 这是全项目**唯一真正受 Python 运行时影响**的热点：openpyxl 解析 xlsx = XML 解析 + 逐单元格构建 Python 对象，**纯 Python 层 CPU 密集**（区别于 SQLite/Qt 这类 C 库调用） |
| 2 | 逻辑**极简**：输入文件路径 → 输出 `List[List[str]]`（`excel_reader.py:24` 的签名就是如此）。**不碰 SQLite、不碰业务口径、不碰 UI** |
| 3 | **`calamine` 一次替换两个库**（`xlrd` 的 .xls + `openpyxl` 的 .xlsx/.xlsm），且语义与 `data_only=True` 一致（读缓存值不计算） |
| 4 | **失败可一键回退**：一个 `USE_CALAMINE` 常量开关 + `try: import ... except ImportError:` 回退到 Python |
| 5 | 业界公开基准显示 calamine 解析 xlsx 比 openpyxl 快约 **5-20 倍**（量级参考，需自行实测） |

#### 试点边界与验证设计

```text
试点范围（严格限定，不得扩大）：
  新增：rust/ 目录（calamine 读取封装，PyO3 绑定）
  修改：app/importer/excel_reader.py（加开关 + try/except 回退）
  禁止：不碰 app/engine/、不碰 app/db.py、不碰 app/ui/、不碰 SQLite

A/B 验证（可证伪）：
  数据集：data/archive/ 下的历史台账存档（importer.py:37-45 的存档规则已保证有真实文件）
  方法：同一批文件，Python 版与 Rust 版各跑一遍
  断言 1（正确性）：逐格 diff 单元格文本 → 必须 100% 一致
  断言 2（性能）：计时对比，各跑 3 次取中位数
  通过判据：正确性 100% 一致 AND 解析耗时下降 ≥ 2 倍

失败回退：
  ① 运行时：USE_CALAMINE = False（一行常量）
  ② 导入时：try: from ._calamine import read_sheet except ImportError: 回退 Python
  ③ 版本级：git revert 该 commit（试点是独立 commit，约 100 行改动）

试点工期：5-8 人日（其中工具链搭建 3-5 人日）
试点判据（重要）：若试点后导入耗时未下降 ≥2 倍 → 永久放弃 Rust 路线，不再讨论
```

**为什么这个试点设计是诚实的**：它是**可证伪的**。如果连"解析 Excel"这个理论上最能受益的模块都拿不到 2 倍收益，那 Rust 路线就可以被数据彻底否掉 —— 这比空谈"Rust 快"有价值得多，也保护用户不再投入。

**但必须提醒**：即便试点成功，收益也只有"导入快 1-2 秒"。而 `importer.py:396-397` 已经把销项文件**解析了两遍** —— **先删掉重复解析（0.5 人日）就能拿到与 Rust 试点相当甚至更好的收益**。请务必先做那个。

## 附录 A：本报告的性能数字假设与校准方法

| 数字 | 假设来源 | 如何校准 |
|---|---|---|
| `_compute` 单次 150-350 ms | 静态推演：约 20,000 次单行查询（含 `setdefault` 急切求值带来的 staff 查询）× 3-8 μs + Python 聚合 50-150 ms | 在 `get_conn` 加计数代理，调 `build_settlement(2025)` 实测 |
| "24 次调用" | 静态统计 `settlement_view.py` 的 14 个调用点（审计报告 3.2 S-2） | 在 `build_settlement` 加计数，点击「各类报表」数打印次数 |
| calamine 比 openpyxl 快 5-20 倍 | 业界公开基准（calamine 官方 benchmark 及社区测试） | 用 `data/archive/` 下的真实存档文件跑 A/B |
| SQLite 单行点查 3-8 μs / rusqlite 1.5 μs | sqlite3 C 库 + Python 绑定常规量级；rusqlite 公开基准 | 本地 microbenchmark（10 万次点查询取中位数） |
| 数据量：3,000 票 / 30 人 / 6,000 笔收款 | 基于业务描述（"每月数百张发票 + 100-200 条费用"×12 月） | 用真实 `data/lawfirm.db` 跑 `SELECT COUNT(*)` |

> ⚠️ **所有性能数字均为静态推演，本报告未执行任何计时或 profile**（环境缺 `qfluentwidgets`、无生产 `data/lawfirm.db`、shell 执行环境失效）。**但结论的定性部分不依赖这些数字的精度**：即便把每个数字上下浮动 3 倍，"24 次调用改成 1 次"与"单次快 50 倍"的相对关系不会改变 —— 前者是 **O(调用次数)** 的常数因子，后者是 **O(单次成本)** 的常数因子，而前者的常数（24 或 121）远大于后者（50）在本场景下的可用部分。

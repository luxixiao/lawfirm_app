## 0. 结论先行（TL;DR）

需求方的方向 **「员工类型不该被代码写死」是对的**，但有三条必须在动手前知道的事实，其中两条**推翻了我们刚才讨论时的共同前提**：

| # | 事实 | 影响 |
|---|---|---|
| **F1** | **改名会把收入打零。** 结算取数的主键不是员工真实类型名，而是被 `norm_type()` **塌陷过**的身份名；一旦改掉「合伙」，`settle_flags_of("合伙")` 查不到行 → 返回 `(False,"")` → 16 名合伙人 income **静默变 0** | 「只要设好结算口径就能参与结算」**在当前代码下不成立** |
| **F2** | 内置保护 **不是完全失效，是「半失效」**：真实生产库里 `合伙/聘用/兼职/行政` 的 `is_builtin` **就是 1**（保护在生效）；只有 `8d17b55` 之后**新建**的库才会因为没人写 `is_builtin=1` 而失效 | 之前我说的「保护失效」只对**新库**成立，对**你这台生产库**不成立 |
| **F3** | `charge_detail.person_type` / `expense_ledger.person_type` 是**历史行级快照**，`rename_type` **从不回写**它们（只改 `staff_type_def.name` + `staff.staff_type`） | 即使改名，旧行仍写着 `'合伙'`；且现状已经存在「分身份 sheet ≠ 汇总」的缺口 |

**一句话结论**：可以去做「数据驱动」，但 **不能只删掉这道保护就了事** —— 那会把 F1 变成静默的金额事故。真正的根因是**「名字塌陷作主键」**（`norm_type` / `_staff_type_orig`），必须先把它拆掉，再谈去重为一个/几个属性。而且**一个 role 字段不够**，审计下来至少需要 4 个正交概念（§2）。

## 1. 事实校正：三条推翻原前提的发现

### 1.1 F1 —— 改名会把收入打零（亲自复核）

你判断的依据是「结算读的是 `settle_flags_of(st["staff_type"])`，读的是实际类型名」。这条**本身没错**，但中间隔着一层**塌陷**：

```python
# app/engine/backfill.py:61-69  ← 塌陷函数之一
def norm_type(staff_type) -> str:
    t = (staff_type or "").strip()
    if "合伙" in t: return "合伙"
    if "兼职" in t: return "兼职"
    if "聘用" in t: return "聘用"
    return "其他"

# app/engine/person_settlement.py:96-108  ← 塌陷函数的第二个副本
def _staff_type_orig(conn, name) -> str:
    ...  # 同样四分支子串匹配，返回 合伙|兼职|聘用|其他
```

而构造人员结构时，**override（身份）优先级高于真实类型**（我复核了源文件原文）：

```python
# app/engine/person_settlement.py:141-144
def _new_st(conn, name, override=None) -> Dict:
    """标准人员结构（override=身份，优先于人员类型）"""
    return {"staff_type": _staff_type(conn, name, override), ...}

# app/engine/person_settlement.py:90-93
def _staff_type(conn, name, override=None):
    if override: return override          # ← 用塌陷后的身份名
    return _staff_type_orig(conn, name)   # ← 另一条也是塌陷
```

最后这一步才是致命的：

```python
# app/engine/person_settlement.py:405-407
is_settle, net_basis = staff_type.settle_flags_of(st["staff_type"], conn)   # ← 拿塌陷名去查类型定义表
... m["income"] = round(m["inv_total"], 2) if net_basis == "开票净额" else round(rec_net, 2)
```

**把「合伙」改名为「啊啊啊」后的两条路径（此时 `staff_type_def` 里没有 `'合伙'` 这行了）：**

| 路径 | 取到的名字 | `settle_flags_of` 结果 | income |
|---|---|---|---|
| 各身份 sheet（`person_type='合伙'` 传入作 override） | `'合伙'`（来自历史快照） | 查不到行 → `(False,"")` | **0** |
| 汇总 sheet（`person_type=None`） | `'其他'`（`_staff_type_orig` 未命中 合伙 子串） | 命中「其他」行 → `is_settle=0` → `(False,"")` | **0** |

> 注：`settle_flags_of` 本身写得是对的（`staff_type.py:163-187` 按名查表），**错的是喂给它的名字是塌陷出来的**。同文件另一个函数 `is_settle_participant()`（`staff_type.py:132-158`）走的就是正确路径——「用 `staff.staff_type` 原样查表」。**同一个概念在系统里有两套解析路径，这是所有风险的根源。**

### 1.2 F2 —— 保护是「半失效」，不是完全失效（亲自复核）

我跑了真实库只读查询，原文输出：

```

  合伙       is_builtin=1  is_settle=1  开票净额
  聘用       is_builtin=1  is_settle=1  收款净额
  兼职       is_builtin=1  is_settle=1  收款净额
```

所以：

- **你这台生产库**：`合伙/聘用/兼职` 的 `is_builtin=1` → `rename_type` / `delete_type` **现在就能正常拦住**。保护没有失效。
- **新建库**：`8d17b55` 移除了预置逻辑后，全仓确实再无代码写 `is_builtin=1`（`add_type` 无条件写 0、`ensure_types` 写 0、`ensure_defaults` 只补列）→ 保护失效。
- **顺带的既存不一致**：库里 **`行政` 的 `is_builtin=1`**，但代码 `staff_type.py:29` 的 `BUILTIN_TYPES` 只有 3 个、不含「行政」。两处内置名单已经漂移。

> 这条是我在上一轮回答里**判断错了**：我当时断言「保护彻底失效、内置三类现在能被改名删除」，实际对你这台生产库不成立。更正如上。

### 1.3 F3 —— 已入库的 `person_type` 快照与「分身份 ≠ 汇总」

```
--- charge_detail.person_type 现存值 ---      ('兼职',1) ('合伙',5) ('聘用',3)
--- expense_ledger.person_type 现存值 ---     ('其他',51) ('兼职',1) ('合伙',59) ('聘用',43)
```

- `person_type` 是**行级快照**（不在 SCHEMA 建表内，由 `db.py:473-477` 迁移加到 `charge_detail` / `expense_ledger`）。
- `rename_type` 只更新两张表（`staff_type.py:265-266`），**不碰**这两张业务表的 `person_type`。

## 2. 消费方语义解剖：一个字段到底够不够？

这是本次审计最核心的问题。结论：**不够。** 代码里依赖三个名字的地方，底层要的业务语义是**四种不同的东西**，压成一个字段会坏菜。

| # | 消费方 | 关键位置 | 它真正要区分的本质 | 能否由 `is_settle`+`net_basis` 推出 | 归类 |
|---|---|---|---|---|---|
| 1 | 各身份 sheet / tab | `person_settlement_exporter.py:143`、`settlement_report_exporter.py:271`、`settlement_view.py:109/240/579/614` | 同一人不同业务行的**结算口径归属**（开票 vs 收款）。**聘用 与 兼职 行为完全等价**（同为收款净额、同为 `rec_net`） | **能**（差异 100% 由 `net_basis` 表达） | ① 可由配置推出 |
| 2 | 开票收入表名单 | `invoice_income_exporter.py:36` `WHERE staff_type IN ('合伙','聘用','兼职')` | **本所执业律师名单完整性**，排除费用池/非业务人员（公共、行政）。注意：**挂靠是有办案业务的，现在被排除是否符合业务意图，存疑** | **不能**（公共/行政 `is_settle=1` 却必须排除） | ② 需「内部/外部」轴 |
| 3 | 年度业务收入结算表（聘用律师） | `staff_income_exporter.py:41` `LIKE '%聘用%' OR LIKE '%兼职%'`、`:99` 表标题、`settlement_view.py:795/817` 导出文件名 | **外部薪酬/个税口径**（雇员律师走工资薪金+五险一金 vs 合伙人走经营所得）+ **对外文件名契约** | **不能**（名单维度与结算口径无关） | ④ 外部契约，不该动 |
| 4 | 公共专属费用校验 | `expense_cat.py:28` `_FORBIDDEN_STAFF_TYPES = set(BUILTIN_TYPES)`、`:183-185` 判据 `norm_type(staff_type_of(...))` | **这笔钱能不能落到某个自然人头上**＝排除费用池与外部人员 | **不能**（`is_settle` 已被「可承担费用」语义污染，见下） | ② 需「内部/外部」轴 |
| 5 | `_TYPE_SUFFIX` 姓名后缀清洗 | `expense_import.py:17` | **外部台账文件的书写约定**（经办人单元格被财务部写成「徐琦合伙」） | 无关 | ④ 导入层格式契约 |

### `is_settle` 目前的语义污染（必须一并处理）

`公共` / `行政` 之所以 `is_settle=1`，是为了通过 `expense_validation.py:85` 的规则③「经办人必须参与结算」——它们是**为了能当费用承担人**才被勾选，**并不产生个人业务收入**。于是「可承担费用」与「有结算收入」两个不同的语义被压缩进了同一个布尔，这正是第 2、4 类无法从 `is_settle` 推导的直接原因。

### 结论：至少需要 4 个正交概念（外加 1 个独立的导入层词表）

| 概念 | 取值 | 喂饱谁 |
|---|---|---|
| **① 结算口径 `net_basis`** | 不结算 / 开票净额 / 收款净额 | 消费方 1（**已存在**，不用新加） |
| **② 内外轴 `scope`** | 本所律师 / 费用池·非业务 / 外部 | 消费方 2 的名单 **+** 消费方 4 的黑名单（同一根轴） |
| **③ 费用承担资格 `can_bear_expense`** | 是 / 否 | 从现 `is_settle` 里**拆出来**，消上面那条污染 |
| **④ 外部报表分类 `report_class`** | 聘用律师 / 合伙人 / 后勤 / 无 | 消费方 3（挂在人员上，或「类型→报表分组」映射表，可按需二选一） |
| **⑤（独立）姓名后缀清洗词表** | 可配置字符串列表 | 消费方 5，属导入层，**不属于员工类型模型** |

> **硬约束**：改造后所有解析必须走 `staff.staff_type` → `staff_type_def` 主键这条路（即 `is_settle_participant` 的写法），**彻底禁止任何形式的名字塌陷**。否则 §1.3 的「分身份 ≠ 汇总」缺口会在第一个新类型出现的当天复现。

## 4. 真实数据迁移风险

| 检查项 | 结果 |
|---|---|
| `staff_type_def` 行数 | **10** |
| `staff` 人数 | **63** |
| `staff_type` 指向**不存在类型**的行 | **1 人**（`'暂估'`，`staff.id=44`，`is_active=1`） |
| `staff_type` 为空 / NULL / 带前后空格 | 均为 0（这块干净） |
| 类型表里**无人引用**的类型 | 2 个（`单独项目`、`实习`） |

结论：

1. **必须迁移**：`staff.staff_type` 是 `TEXT NOT NULL` 且存的是**类型名字符串**（无 `type_id` 外键）。引入新属性意味着要给 `staff_type_def` 加列并回填 10 行。
2. **至少需要 1 个兜底**：62/63 人能映射到现存 10 个类型，**1 人（暂估）无从映射**。
3. **会卡迁移的脏数据只有 1 行**，可控。
4. `'暂估'` 这条孤儿**客观证明**「类型表里没有的类型会落进 `staff` 表」不是理论风险。

## 6. 方案 A 的可行性结论

**可行，但有前提、且不能走捷径。**

- ✅ **技术上可行**：真正的病灶是「名字塌陷作查表主键」+「4 份互不同步的 UI 名单」，都是可改造的显式逻辑，没有架构级阻塞。
- ⚠️ **但不能「只删保护」**：单纯删掉 `rename_type/delete_type` 的 `is_builtin` 判据，等于把 F1 变成**静默的金额事故**（改名后 16 名合伙人 income 变 0，不报错）。这是本方案唯一的**红线**。
- ⚠️ **一个字段不够**：见 §2，需要 4 个正交概念。若压成一个 role 字段，消费方 2/3/4 会各自失真。
- ⚠️ **顺序不能倒**：先拆塌陷（让结算读数直接用真实类型名），再引入属性，最后动 UI/导出/文案。倒过来做会在中间态出问题。

## 7. 需要需求方拍板的开放问题（Decisions）

这几个我**不该替你决定**，你的答复直接决定改造范围：

3. **「聘用」和「兼职」要不要合并？** 二者在结算上行为**完全等价**（同为收款净额）。保留两个名字但同一配置，还是合并？

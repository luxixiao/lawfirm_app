## 一、结论摘要

1. **补录判定改为「只看发票号码」**——不再依赖开票日期。更健壮，且天然覆盖"日期缺失/写错"的坏数据。
2. **复核期补齐可见性**：期外票已有（比对表「需补录」筛选），红字缺原票要在复核期也可见。
3. **复核期补齐确认与修改能力**：复用现有右栏修正面板（`ProblemFixPanel`）。
4. **台账备注的原票号比对本期不做**（以销项导出为准），留后续。
5. **原票号改由销项数据反查**：用红字票的发票号 → `SELECT orig_invoice_no FROM invoice WHERE invoice_no=?`，**无需解析台账备注**（见第八节第 1 点）。
6. **补录改为「随台账一起入库」（pending 模式）**：不再立即写库，点「取消」则一行都不写（见第五节 B2）。

## 二、本轮已核实的事实

### 2.1 导入顺序约束「已存在」
`validate_ledger_before_write()` 校验 1（`app/importer/importer.py:555-568`）：

```
SUM(invoice.total_amount) WHERE strftime('%Y-%m', invoice_date) = 账期
    必须等于    台账 sheet1 + sheet2 合计
```
不等则提示「校验失败 … 请确认已先导入 {账期} 销项文档」。
**豁免分支**：销项合计 = 0 且台账无 sheet1 时不报错（放行）。

→ 结论：用户所述"必须先导入销项导出文档才可导出发票台账"**已作为写前校验存在**。

### 2.2 红字 → 原票号，只有「销项」一个来源（本期不做台账比对）

| 来源 | 现状 |
|---|---|
| 销项导出文档 | ✅ 已实现：`raw_invoice._RED_RE = 被红冲蓝字数电票号码[:：]\s*(\d+)` → `normalize_to_invoice()` → `sync_to_invoice()` 写 `invoice.orig_invoice_no`（`raw_invoice.py:17, 198, 232, 242`） |
| 发票台账 | ❌ 未解析：`parse_remark()` 遇「冲XX发票XX」只标 `is_red_remark=True` 并整段 return；`commit_ledger_import()` 写 `orig_invoice_no=""`（`importer.py:679-683`） |

→ 所以「两份比对、以销项为准」目前**没有第二份可比**；按本轮决定**留后续**。

### 2.3 ⚠️ 开票日期解析失败 = 整份台账导入失败（现状隐藏问题）

- `_parse_invoice_sheet()` 里 `"invoice_date": norm_full_date(...)`（`ledger_import.py:164`）位于 `try/except ImportError_` 块**之外**；
- `normalize_date()` 解析失败**抛 `ImportError_`**（`date_utils.py:106`）；
- 异常冒泡到 `import_ledger_file()`（`importer.py:603`，**无捕获**）→ **整份文件导入失败**，前面能解析的行一起丢。

另外：**空日期不报错**（`normalize_date("")` 返回 `""`）→ 会写 `invoice_date=''`；该列虽为 `NOT NULL`（`db.py:15`）但空串能通过 → 该票**不进任何按月统计**，属静默脏数据。

> 与项目既有原则「解析失败不崩溃、转交互式修正对话框」不一致 —— 建议本期顺带改为**问题行**。

### 2.4 退款侧冗余（供确认）
`refund.orig_invoice_no` 在退款确认时**从红字票复制**（`refund_view.py:306-309`，弹窗只让填金额/日期），不会引入新号。
`list_pending_backfill()` 里 `UNION refund.orig_invoice_no` 仅作**防御性冗余**（唯一作用：红字票被删/回滚而退款记录残留时兜底）。
→ 支撑用户判断：「补录只需看红字票，不用管退款」✅

## 三、工作包 C：补录判定口径修正（核心）

### 新判定规则

> **sheet3 行**：若 `票号 ∈ 库中已有票号` → **不补录**；否则 → **补录**。
> 另加一条硬校验：**sheet3 行的开票月份必须 < 账期**；出现 ≥ 账期的行 → **报错中止导入**（台账文件有误）。

### 关键要点

- **不再需要开票日期**参与判定；开票日期只在"不补录"分支写库时使用。
- 票号**在库**（销项已导入过）→ 开票日期**以库中为准**（台账那格不再采信）。
- 票号**不在库** → 需补录；开票日期由补录弹窗填写。
- 期外票**永远不会进库**（导入时只写镜表）→ 重复导入同一账期，判定结果稳定 ✅
- ~~必须把本批 sheet1/2 的票号并入"将建票"集合~~ → **不再需要**：由上面那条硬校验兜住（sheet3 出现当期票即报错，故不存在"sheet3 与 sheet1/2 同号"的合法场景）。
- 现存的"sheet3 非期外票按普通票建库"路径，按此口径**永远不该走到** → 改为报错。

### 影响文件

| 文件 | 改动 |
|---|---|
| `app/importer/ledger_import.py` | `is_deferred_invoice()` 改为票号集合判定；`split_deferred()` 接收「库中已有票号集合」；把 `invoice_date` 解析挪进 `try` → 转问题行；**新增 A4 硬校验**（sheet3 开票月份 ≥ 账期 → 报错中止） |
| `app/importer/importer.py` | 3 个 `split_deferred` 调用点（`parse_ledger_file` / `_apply_resolved` / `commit_ledger_import`）传集合；`validate_ledger_before_write:575` 同步；去掉对 `is_period_before` 的依赖 |
| `app/engine/raw_ledger.py` | `deferred_sheet3_invoices()` 去掉 `is_period_before` 过滤（其 "invoice 表无该号" 已是同一口径，日期过滤属冗余） |
| `app/engine/backfill.py` | `is_period_before` 标注为历史用途（或删除） |
| `tests/test_deferred_sheet3.py` | 按新口径重写 |

### ⚠️ 风险点（需你定）

**场景**：某张期外票**已被补录**（`invoice.source='manual'`），之后**再次导入**同一账期台账。

按新口径它"在库" → 会被当**普通票并入本批写库**。核查各表影响：

| 表 | 行为 | 结论 |
|---|---|---|
| `invoice` | 已存在 → 只补 `case_no`（`importer.py:672-676`） | ✅ 不覆盖 |
| `charge_detail` | 命中已存在行 → 只更新 `received_override`（`importer.py:692-706`） | ✅ 不重复 |
| `collection` | **先删 `source='import'`，再按台账插一批 `source='import'`** | ⚠️ 与补录留下的 `source='manual'` 收款**并存 → 重复计收款** |

**已确认（2026-09-16）**：票号在库且 `source='manual'` → **跳过建票与分摊**（已补录，勿覆盖），
但**把台账里的收款读进来**、在**复核页**让用户确认后再更新 `collection`。

用户理由：已经补录过 → 不再需要补录；那张票的收款金额与日期**就在这次复核里确认掉**，
不要再引导用户跑一趟「发票补录」页（用户原话：「已经补录完了我还去发票补录页干啥呢」）。

> 实现拆分：批次 1 只做「不建票、不写分摊、不覆盖」并把台账收款随行带出；
> 用户确认后的 `collection` 写入放到**批次 3**（复用 pending 同事务机制），见第十一节 C6。

## 五、工作包 B：复核期确认与修改（含「补录随批入库」）

### B1 复核期就地修改

- 待确认队列中，相关行复用 `ProblemFixPanel`：可改 开票日期 / 开票总额 / 逐经办人（下拉）| 开票金额 | 收款金额 | 收款日期（支持同名多行 → 多期收款）。

### B2 补录不再立即写库，改为「随台账一起入库」（pending 模式，已定 2026-09-16）

- 点「补录原票」→ 弹窗填写 → **只收集为待写入项，不写库**，存进 **`data["backfills"]`**（随 `data` 流转 → 天然按账期隔离）。
- 「确认入库」时，由 `commit_ledger_import(data, period, path)` 在**同一事务**里写补录的 `invoice(source='manual')` + `charge_detail` + `collection`。
- 点「取消」→ 一行都不写（消除"原票已入库、本批未入库"的中间态）。
- 重构方式：`backfill_module.save_backfill()` 拆两层 —— `build_*`（纯计算 + 校验）+ `apply_*(conn, ...)`（用传入 conn、**不 commit**）。现有 `raw_ledger.update_row(conn=None)` 已是同一模式，照抄即可。

**优点**：原子性（补录 + 台账同事务，任一失败全回滚，优于现在逐张自提交）；可取消；与"先确认、后入库"语义一致。

**必须定的 4 点**

| # | 问题 | 建议 |
|---|---|---|
| 1 | 校验时机 | **两次**：弹窗确定时即时校验（反馈快）+ 入库时再校验（防中间态里花名册变动）。同用 `missing_handlers` |
| 2 | 同批重复票号 | 按票号**去重**；第二次点开提示「已在本批待写入」。现状即时写库是 upsert 覆盖、不报错，批量化后必须显式处理 |
| 3 | 「原票是否在库」判定 | 必须把**本批台账将建票的票号**也算进"在库"（判定发生在入库前，本批票都还没进库）——与工作包 C 的并集口径一致 |
| 4 | `received_snapshot` | **不写**；并在比对表把补录票标「补录」来源（或按 `source='manual'` 过滤），避免多出"仅库有"行污染差异统计 |

**另两点**

- 补录票的 `import_batch_id` **留空**（仍只写 `source='manual'`）→ 覆盖式导入 / 回滚批次不会误删补录数据；追溯用现成的 `change_log`。
- **「发票补录」页保持立即写库不变**（它是独立页面、不属于任何批次）；只有"从复核页触发的补录"走 pending 模式。

> **B2 补充：重复票号会不会跨账期？**（2026-09-16 补查代码后的准确版）
>
> **先纠正一个前提**：**现状代码的判定根本不查库** —— `is_deferred_invoice()`（`ledger_import.py:29`）只做
> `sheet3 且 开票月份 < 账期`，是**纯文件属性、无状态**。所以今天"解析时"与"入库时"的判定**必然一致**，
> 与队列时序**完全无关**；今天唯一能出现跨账期的情形是**台账自己在两个月度都登记了同一张票**。
> 只有换成新口径（票号 ∈ 库中票号 → 不补录）之后，判定才**依赖库状态**，时序才开始有意义。
>
> **三条触发路径**：
>
> | 路径 | 跨账期是否会发生 | 原因 |
> |---|---|---|
> | ① 文件夹批量导入 | ✅ **会** | `import_folder`（`import_view.py:218-239`）**先把所有台账文件解析入队**，再一次性 `ledger_queue_ready` 切页；后续账期的判定**早于前面账期的提交** |
> | ② 单文件逐个导入 | ❌ 不会 | 解析 → 立刻进复核页（队列仅 1 项）→ 确认/取消 → `_finish_queue` 清空队列才回导入页；下一个文件导入时上一个已提交 |
> | ③ 单文件 + 中途从侧栏离开复核页 | ✅ **会**（非正常操作） | `_queue_active` 不重置、`_queue` 留在内存，且侧栏**没有任何导航锁**（`main_window.select()` 无守卫）→ 再去导入下一个账期，`open_pending` 走 `_queue_active` 分支**追加**进同一队列 |
>
> **但写入永远是安全的** —— `commit_ledger_import()` 入口（`importer.py:638`）会**再跑一次 `split_deferred`**，
> 即**提交那一刻按最新库状态重判**。所以批量导入的后果是「**复核页显示滞后**」而非「写错数据」：
> 例如老票 `2024-12` 同时登记在 2025-01 与 2025-03 的 sheet3（A4 允许，两期都 > 2024-12），
> 2025-03 复核页仍会显示「需补录」，但你在 2025-01 补录并提交后，2025-03 提交时会重判为"在库" → 走 A2 分支跳过。
>
> **已定修法（用户 2026-09-16 16:36 拍板，必做 → 见批次 2 A5）**：在 `_load_current()`（`import_review_view.py:202`）里
> 对**当前账期重跑一次 `split_deferred`**，让复核页显示与提交口径一致 —— 该方法本就在 load 时重跑
> `validate_ledger_before_write`（`:211`），加一句是**对称**的，改动极小。
>
> **用户口径（原话）**：「既然只有批量导入才会出现这个问题，那就批量导入后，**必须按照顺序一个账期一个账期地确认入库**；
> **每确认一个账期，则刷新数据**。其实只是把导入这个动作一次性化了，实际的操作还是和单个账期导入一样处理。」
> → **完全可行，而且这正好就是 A5。** 队列本来就**严格按顺序、不允许跳序**（`_idx` 只前进，`_advance()` 之后必然
> 载入下一账期，见 `:197-206`），所以"每确认一个账期就刷新数据"的**天然时机**就是**载入下一个账期之前**。
> 落地后 **批量导入与单账期导入的语义完全等价**，不再需要跨账期互斥 / 并集那一套。
>
> **副作用（好）**：A5 之后，**跨账期重复补录被结构性消除** —— 前一账期补录并入库的票，在后续账期重跑判定时

### 问题 2：同批重复票号

**场景**：a) 两张不同红字票引用**同一张原票**；b) 期外票行与红字票行指向同一票号；c) 同账期重复导入、在两份文件里各补一次。

**现状为何"不出事"**：`save_backfill()` 第二次写时 `exist` 命中 → 覆盖 `invoice_date / buyer / total_amount / source`；`charge_detail` 先删 `source='manual'` 再插 → **后写覆盖先写、不报错**，用户并不知道自己填的两遍内容不同。

| 选项 | 后果 |
|---|---|
| **A 按票号去重（建议）** | 同票号只留一条待写；第二次点开提示「该原票已在本批补录过（你填过 X），要编辑它吗？」→ 选择即替换 |
| B 允许重复、入库按最后一条覆盖 | 同现状。风险：悄悄覆盖，用户无感 |
| C 允许重复、入库报错中止（✅ 已定） | 最安全但最烦 |

理由：业务规则复合度高（红字引用 + 期外票 + 重复导入三条路径都可能撞号），"悄悄覆盖"的后果最不可控；

> **范围**：跨账期的部分见**第七节 B2 补充**（要点：现状判定是纯日期、无状态，故与队列时序无关；
> 改成按票号查库后才有时序问题，且**只在文件夹批量导入时出现**，且**只影响显示、不影响写入**）。

### 问题 3：「原票是否在库」的判定范围

**核心**：pending 模式下判定发生在**入库之前**，而**本批台账的票此刻也还没进库**。

**举例**：2025-01 台账 sheet1 有票 `…836111`（本批会建票），sheet3 里也有同号一行。
- 若只查库 → 此刻库里还没有 → 判"需补录" → **误导用户去补一张本批马上就会有的票**。
- 正确集合 = **库中已有票号 ∪ 本批将建票的票号（∪ 本批已补录待写入的票号）**。

| 选项 | 后果 |
|---|---|
| A 并入本批将建票号 | 判定准确 |
| B 不并入（靠"四表互斥"的业务假设） | 代码最简；但台账是**人手维护**，跨表重复写不罕见，一旦出现即误报 |
| C A + 并入本批 pending 票号（建议） | 顺手解决场景 b（刚补录完的票不再被另一行提示补录） |

**已定：都不选 —— 不做并集。**

依据是新锁定的业务规则 **A4**：**sheet3 只含"开票月份 < 账期"的票；出现 ≥ 账期的行即报错中止导入**。
既然 sheet3 里不可能出现本该由本批 sheet1/2 建票的**当期票**，那"sheet1 与 sheet3 同号"就是**非法输入**，
会在 A4 的硬校验上直接拦下 —— 判定阶段不需要再并入本批将建票的票号。代码最简，且不依赖"台账人工维护不会撞号"的假设。

### 问题 4：`received_snapshot` 与批次归属

**快照是干什么的**：`received_snapshot` 按 `(import_batch_id, invoice_no)` 存「源台账声称的收款 expected」+「本批次实际写入 collection 的收款 actual」。**比对表优先读快照**（缺才回退 live collection），这样看到的是"这批导入当时的认定"，不被后续月份收款影响。台账导入时每张票写完 collection 都会 upsert 一条（`_write_collection_for_invoice` → `_upsert_received_snapshot`，`importer.py:206`）。

| 选项 | 后果 |
|---|---|
| **A 不写快照 + 不挂批次（建议）** | 补录视为**独立的修正动作**、不参与批次比对。源 A 的原票**完全不进比对表**（其可见性由红字票行的按钮承载）；期外票已在镜表 → 会进比对表但走 live 回退，通常显示一致 |
| B 写快照 + 挂批次 | 补录票像普通导入票参与比对 → 源 A 会多出"仅库有"行；且补录没有台账行，expected 只能为空 → 显示像异常 |
| C 不写快照 + 挂批次 | 覆盖式导入 / 回滚批次会**连带删掉用户手录的补录数据** → 不推荐 |

**已定：选 A** —— **不写 `received_snapshot` + `import_batch_id` 留空**。
补录视为**独立的修正动作**、不参与批次比对；覆盖式导入 / 回滚不会误删用户手录的补录数据；
追溯走现成的 `change_log`。
